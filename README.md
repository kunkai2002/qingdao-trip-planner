# 青岛一图流 · 行程工作台

**把每天的地点、路线和时间，放进同一张地图。**

左边是某一天的行程，右边是地图，两边永远同时在。切换日期，地图只亮那天的路线；
拖动卡片换顺序，路线、到达时间和路程立刻重算；点地图上的图钉，左边自动跳到对应那一站。

所有数据只存在你自己的浏览器里，不上传任何服务器。

## 产品结构

主对象是**旅行**，不是点位：

```
Trip → TripDay → ItineraryItem → pointId → 地图上的点
```

这是这一版最重要的改动。上一版的主对象是「点位」，所以它能回答「这个地方在哪」，
却回答不了「10 月 1 日上午去哪、中午在哪吃、下午还来不来得及去崂山」——
而后者才是真正的问题。地图仍然是核心视觉区域，但不再是唯一主体。

### 导航

桌面端三栏：**72px 导航栏 · 440px 行程工作区 · 自适应地图**。

| 入口 | 回答的问题 |
| --- | --- |
| 总览 | 这趟准备得怎么样了 |
| 行程 | 这一天几点去哪，路上多久 |
| 探索 | 还有什么值得去，加到哪天 |
| 收藏 | 想去但还没定哪天的 |
| 清单 | 出发前还差什么 |

手机端底部四标签：**行程 / 地图 / 探索 / 我的**。收藏、清单、总览和设置收在「我的」里 ——
四个是标签栏变成菜单之前的上限。

## 数据模型

```js
Trip          { id, title, startDate, endDate, travelers, hotelPointId, notes }
TripDay       { id, date, title, color, startTime, items[] }
ItineraryItem { id, pointId, plannedStart, durationMinutes, transitMode,
                reservationStatus, estimatedCost, note, locked }
```

`ItineraryItem` **只存 `pointId`**，绝不复制点位本身。复制会让数据分叉：
改了地点的名字，行程里还显示昨天那个。

### 迁移

存档有三种形态，全部要能读：

| 存档 | 处理 |
| --- | --- |
| v3（有 `days`） | 直接用，缺字段补默认值 |
| v2（点位 + `myRoutes`，即上一个线上版本） | 五条「按天」预设路线**就是**当时的行程，转成 5 天；自建 DIY 路线各自转成额外一天 |
| v1（`n/c/r/rv/...` 缩写字段） | 先过 `fromLegacyPoint`，再走 v2 那条路 |

迁移结果会**立刻写回磁盘**。否则打开却什么都没改的人，磁盘上仍是旧结构，
每次启动都要重新推导一遍，而且这期间导出的备份也是旧形状。

导出带 `schemaVersion: 3`，同时保留 `v` 字段，所以旧版本仍读得动。
导入任何一份备份都会先做逐条校验：坐标非法、缺 id、缺名字的记录被跳过而不是整份拒绝，
指向不存在点位的行程项和收藏会被剔除。

## 路程与时间是**估算**

没有接路径规划 API，也不打算接：密钥没法安全地放进一个公开的静态包里，
而这个站已经有一个足够脆弱的外部依赖（高德的无密钥瓦片）。

所以 `src/lib/transit.js` 用几何算：大圆距离 × 绕路系数 ÷ 模式速度。

| 模式 | 速度 | 绕路系数 | 固定成本 |
| --- | --- | --- | --- |
| 步行 | 4.6 km/h | 1.28 | 0 |
| 驾车 | 22 km/h | 1.35 | 8 分钟（停车 + 走到车） |
| 地铁/公交 | 24 km/h | 1.40 | 12 分钟（进站 + 等车） |

自动模式：≤1.2km 步行，≤12km 地铁/公交，再远驾车。每一段都可以手动改。
界面上一律标注「估算」。

**它错得稳定且可理解**：不会声称自己有不具备的精度，而且调换顺序时数字总是朝你预期的方向变。
所有调用都走 `RouteProvider` 接口，以后要接高德路径规划是换一个文件，不是重构。

🔴 **`haversine()` 返回的是公里，不是米。** 行程、估算和 `formatDistance` 全部说米。
把它当米读会把 7 公里的一天变成「7 m」，而且不会有任何报错 —— 这个坑在开发过程中真的踩到了。
新代码用 `haversineM()`。

### 优化顺序

`src/lib/optimize.js`：最近邻起手，再用 2-opt 拆掉最近邻必然留下的交叉。
以酒店（如果指定了）为起点。**锁定的地点不会移动**；打分时算的是重建后的**整天**距离，
而不是可动子序列 —— 这才让锁定真正起到约束作用，而不是被跨过去。

它只优化**距离**，不知道营业时间、不知道真实路况、更不知道水族馆适合上午。
所以操作前有说明、操作后可撤销（`Ctrl/Cmd + Z`）。

## 设计系统

### 玻璃只用在该用的地方

上一版的问题不是玻璃做得不好，而是玻璃用得太多：品牌框、搜索框、筛选器、按钮、面板、
弹窗全是玻璃之后，所有元素抢同样的注意力，地图被一堆浮层切碎。
Apple 自己的指南也说 Liquid Glass 属于导航与控制层，不该大量用在内容层。

现在的分工是硬规则：

| 玻璃 | 不透明内容层 |
| --- | --- |
| 左侧导航栏 | 行程卡片、地点卡片 |
| 地图上的悬浮按钮与图层菜单 | 工作区、总览、清单、设置 |
| 弹窗、Toast、引导 | 手机上的地点详情 sheet（`panel--solid`） |

**在玻璃上读一整列行程正是这条规则要防的事** —— 半透明面板叠在移动的地图瓦片上，
文字最难读，而且每个元素都一样响。

### 颜色

砂白做内容底，海蓝做路线和主操作，珊瑚红只留给需要回应的事。

```
--sea-600 #087EA4   --sand-50  #FAF7F0   --coral-500 #EF6A55
--sea-700 #0A6E8E   --sand-100 #F2EBDD   --coral-700 #C1452F
--sea-800 #134D66   --ink-900  #17232B   --roof-600  #B64A3E
```

文字颜色是**在渲染出来的页面上量的**，不是照色板抄的：

| | 浅色 | 深色 |
| --- | --- | --- |
| 标题 `--tx-1` | 16.0 | 13.9 |
| 正文 `--tx-2` | 5.7 | 7.9 |
| 次要 `--tx-3` | 5.0 | 5.7 |
| 主按钮文字 | 5.8 | 5.8 |
| 提醒标签 | 4.5 | 6.6 |

全部过 WCAG AA。深色模式是一套**独立的**深色配色，不是把浅色反过来 ——
反色的砂白是一种很脏的褐灰，而反色只对地图是对的。

### 圆角与动效

大面板 24px · 卡片 16px · 输入框 14px · 按钮 12px。
悬停 160ms · 状态 200ms · 卡片 240ms · 面板 280ms。
`prefers-reduced-motion` 下关掉闪烁、骨架流光和弹出动画。

没有任何东西持续发光或长期漂浮。

## 结构

```
src/
├── data/            点位、地铁线、主题线路、清单、trip.js（日期/金额/时长）
├── icons/           图标注册表 + React 组件 + SVG 字符串（供 Leaflet 用）
├── lib/             坐标、搜索、transit.js（估算）、optimize.js（2-opt）、存储、安装
├── map/             Leaflet 实例与图钉图标
├── components/
│   └── work/        导航栏、行程、探索、收藏、总览、清单、设置、地点详情
├── store/           useStore.js（地图与点位）+ tripSlice.js（行程与撤销）
└── styles/          tokens → glass → base → leaflet-theme → workspace
```

🔴 **样式导入顺序是有意义的。** `workspace.css` 必须在最后：它有几条规则的作用
就是把某个表面**从玻璃手里拿回来**（`.panel--solid`）。同权重选择器，只有源码顺序决定胜负。

🔴 **网格轨道一律写 `minmax(0, 1fr)`，不要写 `1fr`。** `1fr` 等于 `minmax(auto, 1fr)`，
内容的最小宽度会顶开轨道：在 390px 的手机上量到过 532px 的列，在 390px 高的横屏里
量到过 492px 高的工作区。都被 `overflow: hidden` 藏住了，所以看起来没坏，只是够不到。

## 已知的真实限制

- **路程和用时是几何估算**，不是导航结果。见上文。
- **没有照片。** 数据里没有图片字段，也没有可靠的免费图源，所以每个地点用的是按分类
  + id 哈希生成的本地 SVG 封面。它稳定、离线可用、不会加载失败 —— 但它不是照片。
  点位如果有 `imageUrl` 会优先用，加载失败自动退回封面。
- **筛选只提供数据答得上来的维度**：分类、片区、免费、评分、需预约、未安排。
  「室内/室外」和「适合什么时段」很有用，但任何字段里都没有，从备注里猜会产出
  一本正经的胡话，所以宁可没有。
- **住宿价格不计入每人预算**：它是按间按晚算的，混进人均总额会被人数乘一遍。
- **高德瓦片没有 API key，走的是非公开端点**，随时可能加 referer 检查或改地址。
  这是这个站最可能先坏的地方，备援需要 GCJ-02 → WGS-84 反向转换，是正式任务。
- **数据只在这台设备的浏览器里。** 换手机、清数据、卸载都会没。定期「导出备份」。

## 数据说明

评分与人均来自携程 / Tripadvisor 点评均值加官方渠道，是非官方牌价，国庆期间普遍上浮。
点位坐标为近似值，可在详情页点「调整位置」后在地图上拖动修正。

底图为高德栅格瓦片。种子坐标是 WGS-84，首次加载时转换一次到 GCJ-02；
**已经存进 localStorage 的坐标是转换后的，绝不能再转第二次。**
浏览器定位给的是 WGS-84，必须过 `wgs2gcj` 再用，否则蓝点偏几百米。
